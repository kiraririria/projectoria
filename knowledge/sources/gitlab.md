# GitLab Docs: merge request и CI/CD

## pipeline | .gitlab-ci.yml, pipeline, stages, jobs и runner

GitLab CI/CD описывает конвейер в `.gitlab-ci.yml` в репозитории. Pipeline состоит из заданий (jobs), которые выполняют команды на runners. Задания объединяются в стадии (stages). При стандартной схеме задания одной стадии могут выполняться параллельно, а следующая стадия ждёт успешного завершения предыдущей. Свойства заданий и правила запуска определяют, что происходит при событиях репозитория.

Для учебного сайта можно начать с этапов test и build: тесты обнаруживают ошибки, сборка проверяет получение пригодного артефакта. Результаты каждого задания видны в интерфейсе пайплайна.

## needs | Зависимости между заданиями и needs

Ключ `needs` перечисляет задания, результатов которых должен дождаться конкретный job. Это позволяет запускать его, как только готовы нужные зависимости, без ожидания всех остальных заданий более ранних стадий. Такой граф помогает ускорить большие конвейеры. С `needs: []` задание без зависимостей может стартовать сразу.

Например, тесты backend могут ждать сборку backend и стартовать до окончания независимой сборки frontend. Для маленького конвейера последовательные стадии обычно проще читать. Указав `needs`, отдельно проверьте, из каких заданий скачиваются необходимые артефакты.

## artifacts | Артефакты заданий GitLab и кэш

Артефакты (job artifacts) — сохранённые файлы и отчёты конкретного задания, например пакет сборки, тестовый отчёт или сгенерированная документация. Конфигурация `artifacts:paths` указывает пути, а `expire_in` может определить время хранения. Последующие задания могут использовать нужные артефакты, например передать сборку в тестовую среду.

Кэш помогает ускорять повторные запуски, сохраняя заново получаемые данные, например скачанные зависимости. Для файла, который требуется как результат конкретной сборки, используйте артефакт с явной связью с заданием. Для долгоживущих версионных пакетов может подойти реестр пакетов.

## merge-requests | Merge request в GitLab и проверка перед слиянием

Merge request (MR) GitLab объединяет обсуждение, изменения файлов, коммиты, результаты CI/CD и согласования для запроса на слияние. Он связывает исходную и целевую ветки. Команда может просить ревью, разрешать замечания в обсуждениях и делать слияние после выполнения заданных правил.

Практическое применение: открыть MR из ветки задачи, объяснить результат, приложить шаги проверки, исправить замечания и проверить статус пайплайна перед слиянием.
