# Отзывы и технические уведомления в Telegram

Бот только отправляет сообщения через сервер: `#feedback` для отзывов и `#error` для технических сбоев. Webhook, polling, регистрация пользователей и дополнительные запросы к модели не используются. Сервер не пересылает вопросы и историю чата. Комментарий отзыва передаётся в группу по явной отправке пользователя.

## Что настроить самостоятельно

1. В Telegram создайте бота через [@BotFather](https://t.me/BotFather) или используйте уже созданного. Добавьте его в группу `-5336363160` и разрешите отправлять сообщения. Для обычной группы права администратора не нужны, если участникам разрешена отправка. Не вставляйте токен в чат, репозиторий или адрес браузера.
2. Используйте уже подключённую к `projectoria` базу Upstash из Vercel Marketplace. Интеграция предоставляет `KV_REST_API_URL` и `KV_REST_API_TOKEN`; новую базу и дублирующие Redis-переменные создавать не нужно. Этот код не создаёт ресурсы и не выбирает тариф. Для подключения вручную также поддерживаются `UPSTASH_REDIS_REST_URL` и `UPSTASH_REDIS_REST_TOKEN` с правами записи и выполнения `EVAL`.
3. Создайте случайный `FEEDBACK_HASH_SECRET`, минимум 32 символа. Например, локально: `python -c "import secrets; print(secrets.token_hex(32))"`. Один и тот же секрет должен использоваться всеми инстансами одного окружения; не коммитьте его.
4. В Vercel → проект Projectoria → Settings → Environment Variables проверьте, что интеграция добавила пару `KV_REST_API_*` для нужного окружения. Добавьте остальные настройки из таблицы ниже: Telegram и HMAC-секрет. Для вручную добавляемых токенов и HMAC-секрета используйте секретный тип. Настройте Production и Preview отдельно. Если одна база используется обоими окружениями, глобальные лимиты и часть ключей общие; для тестирования можно временно выключать отправку в неиспользуемом окружении. `VERCEL=1` платформа задаёт сама, локально её не устанавливайте.
5. После согласованной публикации изменений выполните Redeploy для нужного окружения: новые переменные не меняют уже работающий деплой.
6. Откройте `/api/feedback/config`: при полной конфигурации ожидается `{"enabled":true}`. Это проверка заполнения настроек, а не подтверждение доступности Telegram/Redis.
7. На закрытом Preview отправьте один явно тестовый отзыв. Только HTTP 201/200 со статусом `sent` означает подтверждённый ответ Telegram. Проверьте появление `#feedback` в группе: так проверяются Chat ID, права бота и доступ к Telegram. Повтор того же запроса с тем же Idempotency-Key не должен создавать второе сообщение.
8. Для проверки `#error` в отдельном Preview с включёнными уведомлениями временно оставьте OpenRouter без ключа, отправьте один вопрос и проверьте `provider_configuration` в группе. Затем восстановите конфигурацию Preview. Не меняйте Production ради проверки. Не создавайте специальный публичный endpoint для имитации ошибок.
9. Проверьте Logs Vercel: события чата и `telegram_alert`, корреляцию по `request_id`. Повторите одну неисправность и убедитесь, что уведомления подавляются. Логи Telegram содержат только результат отправки, без текста и токенов.
10. Проверьте чат, источники, историю и форму на телефоне. При отказе Telegram чат должен продолжать работать; форма не должна сообщать об успешной отправке.

| Переменная | Назначение |
| --- | --- |
| `TELEGRAM_CHAT_ID` | `-5336363160` |
| `TELEGRAM_BOT_TOKEN` | Токен бота; пусто — отправка отключена |
| `TELEGRAM_ALERTS_ENABLED` | `true` включает технические уведомления независимо от отзывов |
| `TELEGRAM_FEEDBACK_ENABLED` | `true` включает приём отзывов независимо от уведомлений |
| `KV_REST_API_URL` | HTTPS REST URL Redis; добавляет Vercel Marketplace |
| `KV_REST_API_TOKEN` | Секретный REST токен с правами записи; добавляет Vercel Marketplace |
| `FEEDBACK_HASH_SECRET` | Случайный секрет, минимум 32 символа; подпись анонимного клиента и HMAC ключей |

В коде флаги по умолчанию выключены. В `.env.example` они включены, но токены и Redis оставлены пустыми. Локальный `.env` не перезаписывается: при подготовке добавлены только отсутствующие настройки. Существующие настройки OpenRouter не меняются.

Приоритет имеет пара `KV_REST_API_URL` / `KV_REST_API_TOKEN`. Если оба значения отсутствуют или пустые, используется альтернативная пара `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN`. Если заполнено только одно значение Marketplace, подключение считается неполным: код не подставляет вторую часть из другого набора, чтобы не смешать адрес одной базы и токен другой. `KV_REST_API_READ_ONLY_TOKEN`, `KV_URL` и `REDIS_URL` не используются. Для проверки только на Vercel переносить Redis-токен в локальный `.env` не требуется; для локальной проверки можно заполнить любую одну полную пару. В URL должно быть обычное `https://`, без обратных слешей из экранированного текста.

## Без Redis

Основной чат, библиотека и история работают. Форма доступна для просмотра, но отправка отключена: `/api/feedback/config` возвращает `enabled:false`, валидный POST — 503. Telegram-уведомления также не отправляются. Штатные логи остаются доступными. Это намеренный безопасный минимальный режим: Python-словарь не используется вместо распределённой защиты. При отказе Redis уже включённая форма возвращает 503 и не обращается к Telegram.

## Ограничения и дедупликация

Проверки выполняются атомарными Lua-скриптами Redis; счётчики общие для всех инстансов. TTL ограничивает хранение. В Redis нет комментариев, вопросов, истории или открытых IP. Идентификаторы клиента, содержимого отзыва и IP представлены HMAC. Анонимный клиент получает функциональную подписанную HttpOnly/SameSite=Strict cookie, Secure на HTTPS. Cookie не является авторизацией и не заменяет IP-лимит; её очистка не обходит общий IP-лимит.

Начальные ограничения отзывов:

- 3 попытки отправки за 24 часа на анонимного клиента;
- 30 попыток за 24 часа на IP, чтобы учитывать общий университетский адрес;
- 1 попытка в минуту на клиента;
- 100 попыток в сутки на весь сервис;
- совпадающее содержимое одного клиента подавляется 24 часа;
- Idempotency-Key действует 24 часа и привязан к клиенту и содержимому.

Учитываются допущенные попытки, включая неподтверждённую доставку. Отклонённые до допуска запросы не расходуют эти квоты. Произвольный `X-Forwarded-For` игнорируется. На Vercel используется платформенный `x-vercel-forwarded-for`; вне Vercel — адрес непосредственного соединения. Для IPv6 используется подсеть /64. При собственном прокси нужна отдельная проверенная конфигурация доверия, иначе будет общий лимит адреса прокси.

Технические уведомления: одинаковый код и стадия подавляются на 15 минут, общий потолок — 5 уведомлений в минуту. Временные ошибки повышаются до уведомления после 5 повторений за 10 минут. Критические конфигурационные ошибки, недоступность базы и HTTP 500 уведомляют сразу с учётом общих лимитов. Request ID не входит в fingerprint, иначе каждый запрос создавал бы новое уведомление.

Не уведомляют о пользовательских 400/403/404/422/429, отмене ответа, отсутствии материалов и обычном rate limit провайдера. Отзывы и отклонённый спам не создают `#error`. Ошибки самого Telegram не запускают новые уведомления. `retry_after` Telegram устанавливает общий Redis cooldown, циклов повторной отправки нет.

## Надёжность доставки и HTTP-коды

`POST /api/feedback` принимает только JSON: обязательный целый `rating` 1–5 и необязательный `comment` до 1000 символов. Дополнительные поля, управляющие символы, некорректный Unicode, body больше 8192 байт и межсайтовые запросы отклоняются. Idempotency-Key передаётся заголовком; перед первой отправкой браузер получает cookie через `/api/feedback/config`.

| Код | Значение |
| --- | --- |
| 201 | Telegram подтвердил новую отправку |
| 200 | Та же отправка уже подтверждена, новое сообщение не создавалось |
| 400 / 408 / 413 / 415 / 422 | Ошибка JSON, времени чтения, размера, Content-Type или данных |
| 403 | Чужой origin или нет корректной cookie формы |
| 409 | Дубликат, конфликт ключа или неизвестный результат предыдущей отправки |
| 429 | Общий лимит; срок ожидания в Retry-After |
| 503 | Нет конфигурации, недоступны Redis/Telegram или доставка не подтверждена |

Telegram Bot API не предоставляет серверного idempotency key. Поэтому гарантировать exactly-once при обрыве соединения невозможно. После неизвестного результата запись остаётся pending на 24 часа: повтор не отправляется и успех не показывается. При явном отказе Telegram бронь освобождается, но квоты попыток и cooldown сохраняются. Отказ после принятия Telegram, но до сохранения результата Redis, также не выдаётся за успех и не вызывает автоматического дубля. Надёжного фонового outbox/очереди в этой версии нет.

Отправка выполняется одним запросом с таймаутом, без parse_mode: HTML и Markdown отзыва остаются обычным текстом. Техническая сводка состоит только из разрешённых кодов, стадий, времени, HTTP-статуса и request_id. Telegram-сообщение ограничено по длине, превью ссылок отключены. URL с токеном редактируется в стандартном HTTPX-журнале.

Функция ожидает завершения уведомления после передачи ответа, без fire-and-forget. Общий предел технического уведомления — 1,9 секунды, обработки отзыва — 5 секунд. Доставка не гарантируется при принудительном завершении функции самой платформой; повторные ошибки всё равно попадут в штатные логи и будут учтены при следующем запросе.

## Интерфейс

Постоянная кнопка доступна в навигации. Форма поддерживает клавиатуру и native radio-кнопки, сохраняет текст при сетевой ошибке, блокирует повторное нажатие. После успеха действует локальный cooldown 60 секунд. Настройки показа находятся в отдельном ключе localStorage и не меняют историю диалога.

После первого подтверждённого ответа по источникам предлагается неблокирующая карточка. Затем — после 10 новых успешных ответов, не раньше чем через 24 часа и не более раза за сессию вкладки. После отправки — пауза 30 дней. При недоступности Telegram-конфигурации автоматическое предложение не показывается. Клиентские счётчики помогают интерфейсу, а не обеспечивают безопасность; при запрете хранилища браузером их сохранность между посещениями не гарантируется.

## Vercel Firewall

На Hobby доступно одно правило Rate Limiting на проект. Если оно уже защищает `/api/chat`, не создавайте второе: расширьте условие до `Method = POST AND (Path = /api/chat OR Path = /api/feedback)`. Для демо можно начать с 10 запросов за 60 секунд на IP, с ответом 429; общий университетский IP потребует корректировки после наблюдения. Это общий бюджет двух endpoint'ов, а не по 10 для каждого. Суточные квоты отзывов остаются в Redis. При большом потоке GET `/api/feedback/config` рассмотрите отдельные доступные WAF-условия или bot protection в пределах тарифа; код не создаёт платных ресурсов.

Приложение не может уведомить о сбое сборки, недоступности домена/DNS, отказе маршрутизации до функции, блокировке запроса Firewall, холодном старте до импорта приложения или принудительном завершении Vercel. Эти события проверяются в Deployments/Logs/Monitoring и средствами платформы.

## Проверки

`python -m pip install -r requirements-dev.txt`, затем `python -m pytest -q` и `node --test tests/frontend.test.mjs tests/feedback.test.mjs`. Тесты используют MockTransport вместо Telegram и тестовый Redis с выполнением настоящих Lua-скриптов; реальных сообщений нет. Для упаковки Vercel новые Python-модули импортируются из `app`, оба JavaScript-файла входят в существующий `app/static/**`; зависимости Redis/Lua нужны только тестам. Облачная сборка и end-to-end доставка требуют настроенного Preview и отдельного разрешения на публикацию.

Источники: [Telegram sendMessage](https://core.telegram.org/bots/api#sendmessage), [Upstash REST](https://upstash.com/docs/redis/features/restapi), [Redis Lua](https://redis.io/docs/latest/develop/interact/programmability/), [Vercel request headers](https://vercel.com/docs/headers/request-headers), [Vercel WAF Rate Limiting](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting).
