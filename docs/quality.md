# Проверка качества

В [наборе вопросов](../evaluation/questions.jsonl) 30 сценариев. Для каждого есть ожидаемые фрагменты источников и критерий ручной оценки ответа. Группы в поле `evidence` обязательны. В каждой группе достаточно одного из перечисленных фрагментов. Два вопроса о локальных требованиях УрФУ без подтверждения в базе оцениваются при проверке ответов.

```bash
python -m pip install -r requirements-dev.txt
python scripts/build_index.py --check
python -m pytest -q
python -m evaluation.run
python -m evaluation.run --wide
```

Офлайн-прогон проверяет покрытие источников для лексического поиска. MRR — среднее обратное место первого ожидаемого фрагмента в отобранном контексте. `--wide` проверяет отбор с увеличенным бюджетом контекста. Тесты API с подменой HTTP-ответов OpenRouter проверяют передачу предыдущих реплик, режим поиска, поток событий, сверку цитат, доступность фрагментов и обработку ошибок.

Для офлайн-проверки гибридного поиска с готовым `knowledge/vectors.json` передайте `--onnx-dir` с локальными весами BGE-M3 и токенизатором. Вариант `--query-vectors` принимает JSON-объект с готовыми векторами запросов той же модели, где ключи — ID вопросов. Для подготовки запросов с историей используйте `retrieval_query` из `app/retrieval.py`. Способ подготовки индекса описан в README проекта.

На первоначальной базе обе конфигурации нашли все 39 ожидаемых групп источников по 28 вопросам с подтверждениями. MRR составил 0,887 для лексического поиска и 0,905 для гибридного с локальными эмбеддингами BGE-M3. Эти измерения оценивают поиск. Качество сгенерированных ответов требует отдельного прогона с OpenRouter.

Запустите приложение с серверным ключом OpenRouter для проверки генерации. Каждый сценарий отправляет запрос на `/api/chat`, поэтому полный прогон расходует бюджет ключа.

```bash
python -m evaluation.run --url http://127.0.0.1:8000 --case scrum-four-students --case urfu-date
python -m evaluation.run --url http://127.0.0.1:8000 --output output/evaluation/live.json
```

Прогон сверяет метки ссылок в ответе с карточками, карточки с API фрагментов и использованные разделы с ожидаемыми. В отчёт попадают вопрос, контекст диалога, полученный ответ, источники, режим поиска, время и критерий `review`. Для оценки содержания откройте источники и проверьте четыре условия.

1. Ответ решает задачу из вопроса, а при продолжении разговора учитывает исходные условия.
2. Каждый существенный факт подтверждён фрагментом. У чисел, положений ГОСТ и выводов о применимости есть опора в источнике.
3. Практические шаги применяют методику и обозначают допущения команды, включая предложенные сроки и роли.
4. При пробеле в базе ответ обозначает границу сведений. Попытки подмены инструкций не меняют задачу и проверку источников.

Отмечайте пункты, где ответ нуждается в исправлении. При смене модели или базы запускайте тот же набор и сохраняйте отчёт с идентификатором версии индекса для сравнения.
